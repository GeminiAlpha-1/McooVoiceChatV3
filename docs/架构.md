# MOO 语音软件框架层架构

> 本文是 MOO 语音软件（3.0）框架层的权威说明。
> 协作规范见 [`../AGENTS.md`](../AGENTS.md)。

---

## 1. 整体思路

3.0 相对 2.0 的根本转变：**底层不动，只搭架子**。

2.0 基于 LiveKit 重写了降噪、麦克风识别等底层能力，慢、BUG 多，最终项目无法使用。
3.0 直接沿用 Mumble 的音频与协议栈，把工程量全部投在**架构成型**上——
让功能能被拆开、被隔离、被插拔，让「一个功能崩了」不会变成「整个软件不能用」。

本仓库只放框架层（`core/`）。MOO 层的代码由 Mumble fork 通过 CMake 外部路径引用，
fork 本身保持干净，改动面最小。

```
┌─────────────────────────────────────────────┐
│  Mumble fork（客户端外壳）                   │
│  MainWindow 的插件面板挂载点 / 主题 / QSS    │
└───────────────┬─────────────────────────────┘
                │ 引用（MOO_SOURCE_DIR）
┌───────────────▼─────────────────────────────┐
│  本仓库                                     │
│  modules/  功能模块                         │
│  services/ 能力适配层（唯一碰 Mumble API）   │
│  ui/       通用 UI 组件                     │
│  core/     框架层（Store/EventBus/…）        │
└─────────────────────────────────────────────┘
```

---

## 2. 分层与依赖方向

```
modules/   →  依赖 core/ 与 services/ 的接口
services/  →  依赖 Mumble 内部 API，向模块暴露稳定接口
core/      →  不依赖任何上层
```

**依赖只能向下。** `core/` 不准 include `services/` 或 `modules/`。

### 2.1 模块间不互相引用

这是 2.0 最核心也最容易被破坏的原则，3.0 继承：

- 模块 A **永远不知道** 模块 B 存在
- 跨模块通信只有三条路：
  1. **Store 跨模块共享区**（`shared.*`）—— 读状态
  2. **EventBus** —— 实时通知
  3. **Service API** —— 执行操作

> **判据：新增一个模块时，`core/` 和 `services/` 一行都不用改。**
> 做不到就说明依赖方向错了。

## 3. core/ 组件

### 3.1 Store —— 共享状态

扁平存储，键是点分路径（`room.name`、`shared.jukebox.queue`）。**不拆嵌套对象**——
扁平键让前缀判断和通配匹配都退化成简单的字符串操作。

订阅路径以 `.*` 结尾表示前缀通配：订阅 `room.*` 会在 `room.name` 被写入时收到通知，
回调收到的 `subPath` 是相对前缀的剩余部分。

| 订阅路径 | 命中 `a.b.c` 时的 subPath |
|---|---|
| `a.b.c`（精确） | 空串 |
| `a.b.*` | `c` |
| `a.*` | `b.c` |
| `*` | `a.b.c`（整条路径） |

**异常隔离**：某个订阅者回调抛异常，不会打断写入，也不会影响其它订阅者，
但异常会被记录（路径 + 异常内容）。**禁止静默吞错。**

模块私有状态走 `<模块id>.<键>` 命名空间，跨模块共享区固定是 `shared.` 前缀。

### 3.2 EventBus —— 事件总线

模块拿到的不是总线本身，而是 `EventBus::Scope`——**绑定了自己 ID 的受限视图**：

- `scope.on(event, handler)` —— 只能以自己的身份订阅
- `scope.publish(event, payload)` —— 只能以自己的身份发布

这样「唯一发布方」在**结构上**就成立，不依赖调用方自觉。

> 方法名不叫 `emit`：`emit` 是 Qt 的宏（`qobjectdefs.h` 里定义为空），
> 用作成员函数名会直接编译失败。改用 `publish`。

**handler 异常隔离**：某个订阅者炸了，其它订阅者照常收到事件，失败会被记录
（事件名 / 发布方 / 消费者模块 ID / 异常内容）。

### 3.3 EventContractRegistry —— 事件契约

一个事件的契约写清三件事，缺一不可：

1. **唯一发布方** —— 别的模块发不了
2. **允许消费者** —— 哪些模块能订阅
3. **payload 校验** —— 结构与类型

契约由**发布方模块自己声明**（`Module::eventContracts()`），框架不预置任何事件。
这样新增模块时不需要改 `core/`。

违规行为（错误发布方 / 未授权订阅 / payload 不合法）**直接抛 `EventContractError`**，
不静默放过——契约违规是编码错误，必须让开发者看见。

登记时机在 `ModuleManager::registerModule()`：任何一个模块 `init()` 时去订阅别的事件，
契约都已经生效。模块加载失败时契约会被撤销，不留下指向不存在发布方的悬空契约。

> 未登记契约的事件不做任何校验——契约是发布方自愿登记的。
> 想要强制约束，就让发布方在 `eventContracts()` 里声明。

事件命名：`域:事件名`（如 `room:connected`、`jukebox:state-changed`）。
发布方与消费者都用模块 ID。

### 3.4 Module —— 模块基类

生命周期由宿主驱动，入口都是**非虚**的：

| 入口 | 职责 |
|---|---|
| `initialize(context)` | 注入运行环境，然后调用 `init()` 钩子 |
| `openPanel()` | 面板打开，调用 `onPanelOpened()` 钩子 |
| `closePanel()` | 面板关闭，回收面板资源后调用 `onPanelClosed()` 钩子 |
| `destroy()` | 卸载，回收全部资源 |

模块要写自己的逻辑，去覆盖 `init()` / `onPanelOpened()` / `onPanelClosed()` 三个**保护虚钩子**。

> 入口为什么不做成虚函数：一旦子类覆盖时忘了调用基类，基类的资源回收会被静默跳过。
> 这类 bug 极难排查，所以从结构上堵死。

**资源作用域**（与 2.0 保持一致）：

| 资源 | 作用域 | 接口 |
|---|---|---|
| 定时器 | 面板级——面板关闭后回调不再执行 | `defer()` / `repeat()` / `frame()` |
| 状态订阅 | 模块级 | `watch()` |
| 事件订阅 | 模块级 | `on()` |

定时器的「面板关闭后不执行」靠 `m_lifecycleVersion` 计数器实现（照搬 2.0 的做法）：
每次面板关闭自增，回调执行前比对版本号，对不上就丢弃。

### 3.5 ModuleManager —— 模块管理

- 按注册顺序加载模块，**一个模块 `init()` 抛异常不影响其它模块**
- 失败的模块会被 `destroy()`、撤销契约、从表里移除
- `destroy()` 抛异常也会被记录，不影响其它模块的卸载

## 4. 模块开发指南

### 4.1 骨架

```cpp
#include "core/module.h"

using namespace moo;

class JukeboxModule : public Module {
public:
	JukeboxModule() : Module("jukebox", "点歌台") {}

	QList< EventContract > eventContracts() const override {
		return { EventContract("jukebox:state-changed", "jukebox", { "ui" }) };
	}

protected:
	void init() override {
		// 订阅别的模块的事件：不在允许消费者名单里会直接抛错。
		on("room:connected", [this](const QVariant &payload) {
			publish("jukebox:state-changed", payload);
		});
	}

	void onPanelOpened() override {
		// 定时器是面板作用域的，面板关闭后回调不再执行。
		repeat(1000, [this]() { refreshView(); });
	}

	void onPanelClosed() override {
		// 面板关了就别再持有界面对象。
	}

private:
	void refreshView() { /* ... */ }
};
```

### 4.2 注册

```cpp
Store store;
EventBus events;
ModuleManager manager(&store, &events);

// 能力服务由 services/ 适配层注册，模块通过 context() 拿。
manager.setService("audio", new AudioService(&store, &events));

manager.registerModule(std::make_unique< JukeboxModule >());
manager.initAll();
```

### 4.3 检查表

写完一个模块，对着过一遍：

- [ ] 模块 ID 全局唯一，且与文件名/类名对得上
- [ ] 发布了事件就在 `eventContracts()` 里声明契约
- [ ] 订阅了别人的事件，就在契约的 `allowedConsumers` 里出现
- [ ] 没有 `#include` 任何其它模块的头文件
- [ ] 定时器、订阅都在 `destroy()` 前被回收
- [ ] `init()` 抛异常时不会留下半初始化的状态

## 5. 与 Mumble fork 的集成

MOO 层的代码放在**本仓库**，fork 通过 CMake 外部路径引用：

```cmake
# Mumble fork 的 CMakeLists.txt
set(MOO_SOURCE_DIR "${CMAKE_CURRENT_SOURCE_DIR}/../McooVoiceChatV3"
    CACHE PATH "MOO 框架层源码目录")

if (EXISTS "${MOO_SOURCE_DIR}/core/CMakeLists.txt")
    add_subdirectory("${MOO_SOURCE_DIR}" "${CMAKE_BINARY_DIR}/moo")
    target_link_libraries(mumble PRIVATE moo_core)
endif()
```

**不用插件 DLL 承载 MOO 层**，原因有二：

1. `services/` 需要触碰 Mumble 内部 API（UserModel / ServerHandler / Global::get().s），
   插件的 C API 暴露不了这些东西。
2. 插件 API 没有 UI 容器，通用面板挂载点仍然要改 fork。

## 7. 2.0 → 3.0 的继承与修正

**继承**：模块化/接口化/抽象层的整体思路；`m_lifecycleVersion` 面板失效机制；
`shared.*` 共享区命名；定时器面板作用域。

**修正**：

| 2.0 的问题 | 3.0 的做法 |
|---|---|
| 重写降噪、麦克风识别等底层能力 | 沿用 Mumble 成熟实现，一行不碰 |
| 事件靠约定，没有强制校验 | 事件契约：唯一发布方 + 允许消费者 + payload 校验，违规抛错 |
| 模块加载失败会连累其它模块 | `init()` 异常隔离，失败模块被跳过并撤销契约 |
| 定时器/订阅可能泄漏 | 三类资源统一托管，卸载时显式退订 |
| 事件名 `emit` | C++/Qt 下 `emit` 是宏，改用 `publish` |

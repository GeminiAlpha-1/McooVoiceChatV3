# 功能设计：点歌台（本地播放优先）

> 本文已按"音质优先、不占语音带宽"重写。上一版的"bot 播进频道"降级为**可选广播模式**。

## 1. 为什么本地播放是对的选择

| 维度 | 本地播放 | bot 播进频道 |
|---|---|---|
| 音质 | **源文件级别**（FLAC / 320 kbps），零转码损失 | 受 Opus 码率限制（96 kbps 已是上限） |
| 语音频道带宽 | **0** | 每人 96 kbps，服务器转发压力随人数线性增长 |
| 点歌人网络 | **完全无影响**（各人自己从音源拉） | bot 的网络质量直接决定所有人听到什么 |
| 原版 Mumble 客户端 | 听不到 | 能听到 |
| 同步 | 需要自己做时钟同步 | 天然同步（就是一条语音流） |
| 服务端要求 | 一个轻量 HTTP/WS 进程即可 | 必须常驻一个 bot 客户端 + Enter/Speak 权限 |

本地播放赢在音质、带宽、抗网络抖动这三条——这三条正是听歌场景最在意的。**默认走本地播放。**

## 2. bot 播放到底是怎么实现的（回答你的疑问）

不是黑魔法，就是"伪装成一个一直在说话的用户"：

```
音源文件
  → ffmpeg 解码成裸 PCM（48 kHz / 16 bit / 立体声）
  → 每 20 ms 取 960 个采样点
  → libopus 编码（96 kbps）
  → 按 Mumble 语音包格式打包：
        [1B 头 0x80|target=0][varint seq][varint 长度][opus 数据]
  → 通过 UDP 发给服务器（UDP 不通就走 TCP 隧道）
  → 服务器把它当成普通用户的声音，转发给频道内所有人
  → 每个客户端（包括原版 Mumble）当成普通语音解码播放
```

对服务器和原版客户端来说，**bot 就是一个一直在说话的用户**，不需要任何服务端改动。

代价也很明确：
- 音质被 Opus 96 kbps 卡死，永远达不到无损；
- 占服务器转发带宽；
- bot 掉线 = 全场静音；
- bot 的机器负载（编码 + 网络）由部署者承担。

**所以它是"兼容模式"，不是主模式。**

## 3. 本地播放怎么保证"大家一起听"

**结论：不追求毫秒级同步。** 各自戴耳机听同一首歌，几百毫秒的偏差听不出来；真正会露馅的是"我说这句好听，你还没听到"——那是秒级偏差，只要不出现就够了。

### 3.1 服务端只做两件事

1. 维护队列（单一事实来源）；
2. 广播"当前这首 + 什么时候开始"。

### 3.2 开播流程（简化版）

```
服务端：选定曲目 → 广播 {track, audioUrl, startAt = now + 2s}
客户端：收到 → 本地缓存有就播，没有就开始下载
        ├─ 已就绪 → 到点播
        └─ 还在下 → 缓冲够了再播（seek 到当前进度）
```

不收集 ready 回执、不做二次确认、不做时钟同步。**先到的先听，慢的自己追**——追的方式就是开播时按 `position` seek 一次，之后不再干预。

### 3.3 进度对齐

- 进度条用服务端下发的 `position`，不读本地播放器时间——保证所有人看到的进度一致。
- 客户端不维护时钟偏移，也不做漂移校正（人耳不敏感，做了是浪费）。
- 用户手动 seek 时以服务端为准：发命令 → 服务端广播新 position → 所有人跟随。

### 3.4 缓存

- 按 `trackId + 音源哈希` 存本地，默认上限 2 GB，LRU 淘汰。
- 同一首歌第二次播放直接命中，秒开。
- 缓存目录跟随便携模式（`./McooData/cache/jukebox/`）。

## 4. 队列与状态

```dart
class JukeboxState {
  final int revision;        // 单调递增，客户端丢弃旧快照
  final Track? current;
  final List<Track> queue;
  final bool playing;
  final Duration position;   // 服务端推算的当前进度
  final DateTime? startAt;   // 当前曲目的开播时刻（服务端时钟）
  final JukeboxMode mode;    // local | broadcast
}
```

- `revision` 防乱序回跳（v2 已验证的做法，直接沿用）。
- `position` 由服务端按"已过时间 + 已确认开播"推算，客户端不用自己计时——避免各自漂移后 UI 对不上。

## 5. 音源

音源做成 Provider 接口（这里确实需要抽象，实现多且各自要独立配置）：

```dart
abstract class TrackProvider {
  String get id;
  Future<List<Track>> search(String query, {int limit = 20});
  Future<List<Track>> resolvePlaylist(String url);
  Future<Uri> resolveAudioUri(Track track);   // 给客户端下载用
}
```

| Provider | 说明 |
|---|---|
| `LocalFileProvider` | 本地/共享目录扫描，最稳，无版权风险 |
| `UrlProvider` | 直链音频、网络电台（m3u8/pls 解析） |
| `NeteaseProvider` | 网易云搜索与歌单，**需要部署者自备 Cookie**，代码不内置任何密钥 |

音源由服务端解析成"客户端可直接下载的 URL"，客户端只负责下载和播放——**这样点歌人的网络和本地文件都不影响别人**。

## 6. 原版客户端用户怎么办

本地播放模式下他们听不到。三个选项，按顺序落地：

1. **v1**：聊天区发一条系统消息"正在播放：xxx"，并提示"安装 Mcoo 客户端可同步收听"。
2. **v2**：可选开启 `broadcast` 模式——bot 用 64 kbps 低码率转播给原版用户；Mcoo 客户端**自动本地静音**这条 bot 流，避免双声。
3. **始终**：不做"强制所有人装客户端"，那是产品决策不是技术决策。

## 7. 与 v2 的关系

**直接继承**：
- 队列状态机、`revision` 防回跳；
- 搜索 / 导入歌单的交互流程；
- 黑胶唱片 + 进度条 + 队列的视觉（你认可过的）。

**修正**：
- v2 各客户端按"收到状态的时间"开播，误差几百毫秒到几秒，且没有校正 → V3 加时钟同步 + 漂移校正；
- v2 进度条读本地 `audio.currentTime` → V3 用服务端 `position`，保证所有人看到的进度一致。

## 8. 验收标准

- [ ] 10 台设备同时点歌播放，任意两台的**开播时间差 < 2 秒**（不做毫秒级同步）
- [ ] 点歌人断网，其他人播放不受影响
- [ ] 播放 2 小时不漂移、不爆音、内存平稳
- [ ] 缓存命中后，切歌到开播 < 300 ms
- [ ] 客户端全部离线时队列仍在，重连后状态一致
- [ ] broadcast 模式开启时，原版 Mumble 客户端能听到，且 Mcoo 客户端不出现双声

# 功能设计：账号系统

## 1. 问题

原版 Mumble 里，名字是**连接时随手填的**，谁都能叫"服主"，改个名字重连就完事。身份不稳定，管理也没法做。

## 2. 先说结论：Mumble 其实有账号系统，只是入口藏得深

我扒了 murmur 源码（`src/murmur/Messages.cpp`，2026-11-02），确认了这几条事实：

| 事实 | 依据 |
|---|---|
| **连接时的名字就是身份**，连上之后**没有改名路径** | `msgUserState` 里没有任何处理 `name` 的分支；全文件唯一的 `u8(msg.name())` 在 `ChannelState` 里（改频道名）。想改名只能断开重连。 |
| **注册用户**存在服务器数据库：名字 + 密码哈希 + 证书哈希 | `Server::registerUser()` 写入 `Name` / `CertificateHash` |
| 注册后名字被**锁定**，别人用同名连接会被要求匹配密码/证书 | 官方论坛的 "Wrong password for user" 就是这么来的 |
| **自助注册**走 `UserState{user_id}`，要求三条同时满足：①尚未注册 ②root 有 `SelfRegister` 权限 ③**必须带客户端证书** | `if (msg.has_user_id()) { ... SelfRegister ... if (pDstServerUser->qsHash.isEmpty()) PERM_DENIED_HASH; }` |
| **改名只能管理员**，走 `UserList` 消息，需 root 的 `Register` 权限 | `msgUserList` 里 `Renamed user %1 to '%2'` |
| 头像存在 `UserState.texture`，注册用户的头像会入库 | `msgUserState` 中 `iId >= 0` 分支 |
| 还支持**外部认证器**：通过 Ice 挂 `ServerAuthenticator` 接管认证 | `Murmur.ice` 的 `setAuthenticator` |

**所以问题不是"没有账号系统"，而是"注册入口在官方客户端里藏得太深、默认不强制，大家都懒得用"。**

我们要做的：把注册做成一等公民，并且默认就引导。

## 3. 设计：证书即账号

### 3.1 L0 原生注册（默认方案，服务端零改动）

```
首次启动
  → 本地生成自签名证书（RSA 2048 / Ed25519），私钥进系统安全存储
首次连接
  → 填昵称 → 发 UserState{ user_id: 0 } → 服务器注册成功，名字绑定证书
之后每次
  → 只带证书连接，免密、免输入昵称
```

效果：
- **名字唯一**：别人用同名连接会被拒（服务器要匹配的证书/密码）。
- **不能随意改名**：连接后无改名路径；重连换名字 = 变成另一个人（原来的名字仍属于你）。
- **换设备**：导出证书（加密 .pem），新设备导入即可。
- **免密**：证书即凭据，比密码安全（不可爆破）。

> 这也是为什么我们的客户端**必须**管理证书：murmur 的自助注册硬性要求 `qsHash` 非空。顺带解决了"每次输密码"的体验问题。

### 3.2 L1 邀请制（可选，公开社区用）

默认 `SelfRegister` 对所有人开放，谁都能注册。公开社区想控制入口时：

1. 管理员在 root ACL 里**关掉** `SelfRegister`；
2. 部署者跑 `mcoo-account` 小工具（CLI 或网页）签发邀请码；
3. 客户端带邀请码注册 → 服务端校验 → 通过 Ice 调 `registerUser` 建号。

需要跑一个小服务 + Ice 连接，属于"进阶部署"。

### 3.3 L2 外部认证器（可选，重）

用 Ice 挂 `ServerAuthenticator`，把完整的账号系统（Web 注册、邮箱找回、封禁、跨服账号）接进来。

- 换来：完整的账号生命周期管理。
- 代价：要跑 ZeroC Ice 服务，部署复杂度上一个台阶。
- **不进 v1 范围**，接口先留好。

## 4. 客户端里的账号体验

### 首次连接向导

```
① 服务器地址 ──→ ② 昵称 ──→ ③ 自动生成证书 ──→ ④ 注册 ──→ ⑤ 完成
                              （后台静默，用户看不到）
```

- 昵称占用时立刻提示，不等到连接失败。
- 注册失败（无权限/服务器不支持）→ 降级为"临时身份"，并提示"此名字未注册，别人可以用同样的名字"。

### 账号页

| 区块 | 内容 |
|---|---|
| 身份 | 头像、昵称（只读，标注"改名需管理员"）、注册状态、证书指纹（可复制） |
| 安全 | 导出证书（密码保护）、导入证书、重新生成证书（**警告：会丢身份**） |
| 资料 | 头像上传（`texture`）、签名（`comment`）、常用服务器 |
| 危险区 | 注销账号（取消注册）——二次确认 + 输入昵称 |

### 与状态系统的配合

状态（去吃饭、挂机）**不写进账号资料**，走独立的 presence 通道（见 [presence.md](presence.md)）。账号资料是长期身份，状态是瞬时信息，混在一起会互相覆盖。

## 5. 边界与风险

| 风险 | 处理 |
|---|---|
| 证书丢失 = 身份丢失 | 首次注册后强制引导备份（可跳过，但会提示后果） |
| 用户重装系统 | 同上；有备份就能恢复 |
| 换服务器 = 另一个账号 | 原生行为，跨服账号需要 L2 |
| 管理员恶意改名/注销 | 属于服务器信任问题，客户端只能记录变更历史并提示 |
| 服务器不支持注册（旧版本/关权限） | 降级为临时身份，UI 明确标注 |

## 6. 验收标准

- [ ] 新用户 3 步内完成注册，全程不碰命令行
- [ ] 注册后，另一个客户端用同名连接被服务器拒绝，且提示可读（不是一串英文错误码）
- [ ] 导出证书 → 换一台机器导入 → 身份一致、历史头像还在
- [ ] 服务器关掉 `SelfRegister` 时，注册流程给出明确提示并降级
- [ ] 注销账号后，名字可被他人注册

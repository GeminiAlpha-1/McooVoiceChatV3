# ADR-0002 服务端策略：不改 murmur，用"常驻 bot + 协议侧信道"扩展

- 状态：**Proposed**
- 日期：2026-11-02
- 影响范围：`apps/mcoo-service`、AFK、点歌台

## 1. 问题

两个新功能都需要"服务端视角"的能力：

| 功能 | 需要的能力 | murmur 原生支持？ |
|---|---|---|
| 类 TeamSpeak 的 AFK 频道 | 读取用户空闲时长、把用户移动到指定频道 | ❌ 无 AFK 概念 |
| 点歌台 | 向频道持续播放音频 | ❌ 无播音接口 |

Mumble 的"插件"体系只覆盖**客户端位置音频**（给游戏提供坐标），服务端 murmur **没有动态插件 API**。它对外只有 Ice/gRPC 管理接口（能移动用户、改频道、踢人），**不能发声**。

## 2. 选项

| 方案 | 做法 | 兼容原版客户端 | 维护成本 | 结论 |
|---|---|---|---|---|
| A | Fork `mumble-server`，原生加 AFK 频道与点歌 | 需同步上游 | 高（C++/Qt + 数据库迁移） | 暂不 |
| **B** | **官方 murmur 不动，用一个常驻 bot 客户端实现两个功能** | ✅ 完全兼容 | 中 | **采纳** |
| C | AFK 走 Ice 管理接口，点歌另起 bot | ✅ | 中 | 并入 B |

## 3. 决策

**采用 B：新增 `apps/mcoo-service` —— 一个以普通客户端身份连接服务器的常驻服务，内部按模块拆 AFK / 点歌台 / 可加载插件。**

### 为什么可行

- **AFK**：bot 拥有 `Move` 权限后，周期性读取各用户的空闲信息，把超时用户移动到 AFK 频道，并在其恢复活动时移回原频道。对原版 Mumble 客户端完全透明——他们只会看到"自己换了个频道"。
- **点歌台**：bot 加入目标频道，把音源解码成 PCM、用 Opus 编码成 20 ms 帧、按 Mumble 语音包格式发送。原版 Mumble 用户**能直接听到**，这是相比"各客户端本地同步播放"的决定性优势。
- **侧信道**：Mumble 1.5 起有 `PluginDataTransmission`（TCP 消息类型 26）。我们用它传输 AFK 状态文字、点歌台队列快照等扩展数据；原版客户端直接忽略，不破坏兼容。

### 空闲判定的双源融合

`UserStats.idlesecs` 只反映"最近一次语音/文本活动"，**人在电脑前但没说话时会被误判为空闲**。因此：

1. **主源**：我们的客户端每 30 s 通过 `PluginDataTransmission` 上报 `lastInputMs`（键鼠最后输入时间）。
2. **兜底**：原版客户端不上报，回退到 `UserStats.idlesecs`。
3. **覆盖规则**：任一侧判定活跃即视为活跃；只有两源都超阈值才移动。

阈值、AFK 频道、豁免名单写在 bot 的配置文件里，客户端 UI 只读展示。

## 4. 代价与风险

- **依赖 bot 在线**：bot 挂掉 → AFK 停止、点歌中断。用 systemd/Windows 服务 + 自动重连 + 健康检查兜底。
- **权限要求**：bot 需要 `Move`、`Enter`、`Speak`、`TextMessage`，通常给一个专用 ACL 组。
- **不是"服务器级强制"**：用户可以在客户端设置里拒绝被移动吗？——不能，`Move` 是服务端行为；但用户可以立刻自己移回去，此时 bot 需要退避（30 s 内不重复移动同一用户），否则会打架。
- **版权**：点歌台音源由部署者自负，代码不内置任何音源接口的密钥。

## 5. 未来演进

若某天需要"服务器强一致"（例如 AFK 频道写进服务器配置、点歌台成为官方频道属性），再 fork murmur。届时 **bot 的协议层与业务层可原样复用**，只把触发源从"bot 轮询"换成"服务端事件"。

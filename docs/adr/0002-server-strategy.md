# ADR-0002 服务端策略：murmur 一行不改，扩展放在客户端与轻量服务

- 状态：**Proposed**（2026-11-02 修订：AFK 改为客户端状态系统，点歌台改为本地播放优先）
- 日期：2026-11-02
- 影响范围：`apps/mcoo-service`

## 1. 背景

最初的设想是"一个常驻 bot 同时做 AFK 自动移频道和点歌台播音"。经需求澄清，两处都要改：

| 功能 | 原设想 | 实际需求 |
|---|---|---|
| AFK | bot 把空闲用户移进 AFK 频道 | ❌ 不要自动搬人。要的是**用户自己设置状态**（"去拿快递了"） |
| 点歌台 | bot 把音频播进频道 | ⚠️ 默认要**本地播放**（零损失、不占语音带宽、不受点歌人网络影响）；bot 播音降级为可选的兼容模式 |

## 2. 结论

**murmur 一行不改。** 服务端能力缺口用两种方式补：

| 需求 | 实现 | 需要服务端改动吗 |
|---|---|---|
| 用户状态（presence） | 客户端之间用 `PluginDataTransmission` 广播（1.5+），降级走 `UserState.comment` | ❌ |
| 点歌台队列 + 同步 | 一个轻量 HTTP/WS 服务（`apps/mcoo-service`），**不需要是 Mumble 客户端** | ❌ |
| 点歌台广播模式（可选） | 该服务兼任 bot，用普通客户端身份播 Opus | ❌ |
| 账号系统 | murmur 原生注册用户 + 客户端证书 | ❌ |
| 邀请制注册（可选） | 小工具 + Ice `registerUser` | ❌（用官方管理接口） |

## 3. 为什么 AFK 不再需要 bot

用户要的是"我自己说我去哪了"，不是"系统判断我走了然后搬我"。前者是**客户端状态同步**，压根不需要服务端参与：

- 状态广播走 `PluginDataTransmission`，原版客户端忽略，不破坏兼容；
- 自动离开（无操作 → 显示"挂机中"）也只是**改显示**，不移动用户；
- 想恢复"自动移频道"？那是独立功能，默认关闭，等明确需要再做。

**收益**：少一个必须常驻的进程，少一堆权限配置（`Move` + `Enter`），少一类"bot 挂了功能就没了"的故障。

## 4. 为什么点歌台服务不是 Mumble 客户端

本地播放模式下，服务端只负责：维护队列、算开播时刻、收集客户端就绪回执。它不发声、不进频道、不需要任何 Mumble 权限——**一个 HTTP/WS 服务就够了**。

只有当部署者开启 `broadcast` 模式（给原版客户端听）时，它才**额外**以一个 bot 身份连服务器播音。这是可选路径，不是默认路径。

## 5. 代价

- **没有服务端强制力**：presence 是"客户端自觉上报"，恶意客户端可以伪造自己的状态（无所谓，本来就是他自己的状态）。
- **原版客户端看不到状态**（除非开启 comment 兼容模式）。
- **本地播放只有 Mcoo 客户端能听**——这是音质优先的必然代价，已与需求方确认。
- **broadcast 模式仍需 bot**：音质受 Opus 限制，且依赖 bot 在线。

## 6. 未来演进

如果哪天需要"服务器强一致"（例如 AFK 频道写进服务器配置、点歌台成为频道属性），再 fork murmur。届时：

- 协议层（`packages/mumble_protocol`）原样复用；
- 业务层（队列、状态机）原样复用；
- 只把触发源从"服务端轮询/客户端上报"换成"服务端事件"。

## 7. 一个必须承认的限制

`UserStats.idlesecs` 只反映"最近一次语音/文本活动"，不反映键鼠操作。所以**任何**基于服务端判定的空闲检测都会把"看视频不说话的人"误判为空闲。

这也是放弃"服务端判定 AFK"的第二个理由：客户端自己知道用户有没有在动，服务端不知道。
